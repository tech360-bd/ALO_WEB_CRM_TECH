## A. Existing System Inventory

### A.1 Stack (confirmed, unchanged — no new framework/DB/auth introduced)
- **Framework:** Next.js (App Router), TypeScript, React — `package.json`, `next.config.ts`.
- **ORM/DB:** Prisma, MySQL (`prisma/schema.prisma` → `datasource db { provider = "mysql" }`). Hundreds of models.
- **Auth:** Mixed — bcrypt password hashing (cost 12) is used consistently everywhere passwords are set. Sessions are DB-backed opaque tokens (`crypto.randomBytes(48).toString('hex')`, 7-day/24-hour expiry) in two parallel tables (`PortalSession`, `StudentSession`), **plus** a third, separate NextAuth (`next-auth`) credentials-based session for `User`/staff logins (`src/lib/auth.ts`, `getServerSession`). Three different login/session mechanisms coexist (see A.3).
- **Tests:** Vitest (unit + integration), Playwright config present for e2e (not run — no live server/DB).

### A.3 CRITICAL FINDING — two parallel student identity/auth stacks already exist in the codebase (pre-existing, not introduced by this session)
Verified by reading the actual registration/login/session code on both sides:

| | **Stack A — "Portal" (live, public-facing)** | **Stack B — "Canonical/Student" (legacy, more feature-complete)** |
|---|---|---|
| User table | `PortalUser` | `User` (NextAuth) |
| Student profile table | `PortalStudentProfile` (`studentId` format `ALO-S-YYNNNN`) | `Student` (`studentId` format `AE-YYYY######`, generated by `src/lib/student/canonical-student.ts`) |
| Register endpoint | `/api/portal-auth/register` — **this is the one actually wired to the live public registration UI** (`src/components/auth/RegisterPage.tsx` → `usePortalStore().register()` → `fetch('/api/portal-auth/register')`, confirmed in `src/lib/stores/portal-store.ts`) | `/api/auth/register` → `registerStudentAtomically()` (atomic, P2002-safe, idempotent by design) — **not called by the live registration form** |
| Login/session | `/api/portal-auth/login` → `PortalSession` table, Bearer token in `localStorage('portal_token')` | `/api/student/auth/login` → `StudentSession` table (`src/lib/student-auth.ts`), **or** NextAuth cookie session for staff |
| Feature surface wired to it | Registration, login, forgot/reset password, OTP | ALL of: Documents (`Document`), Payments (`Payment`), InterviewSessions, VisaReadinessAssessments, Referrals, StudentNotifications, `/api/student/*` (appointments, sop, cv, notifications, referrals, visa-readiness, next-action, applications, dashboard, messages) — these all foreign-key to `Student`, **not** `PortalStudentProfile` |

**Consequence (verified by code inspection, not assumption):** a student who registers today through the real, live public registration form (Stack A) gets a `PortalUser` + `PortalStudentProfile` row, but **no `Student` row is ever created for them**, and nothing in the codebase bridges the two by studentId before this session's fix. That means, prior to this session's repair (Section C), a freshly self-registered student had:
- no CRM `Lead` record, no scoring, no counselor auto-assignment (Section B.1), **and**
- no path to ever get a `Document`/`Payment`/`InterviewSession`/`VisaReadinessAssessment` row, because every one of those features is only implemented against the `Student` model, which self-registration never populates.

This is the single largest architectural finding of the audit and is exactly the "duplicate student records / parallel system" risk the task explicitly warned against — except it **already existed** in the codebase before this session began. See Section F for why a full merge was **not** attempted this session (too large/risky to do safely without a live DB to verify pre/post integrity), and the recommended remediation path.

## B. Issues Found (all verified by direct code reading; none assumed)

### B.1 [FIXED] Student self-registration created no CRM lead and never triggered counselor auto-assignment
`src/app/api/portal-auth/register/route.ts` (the route the live registration form actually calls) only created `PortalUser` + `PortalStudentProfile`. It never created a `Lead`, never called `scoreLead()`/`autoAssignCounselor()`, and never populated the very fields the schema already has for exactly this purpose (`PortalStudentProfile.counselorId`, `.counselorName`, `.journeyStage`, default `"lead_created"`). Confirmed no code anywhere in the repo ever wrote `counselorId` onto `PortalStudentProfile`.

### B.2 [FIXED] Public inquiry/consultation forms on country/destination/test-prep pages bypassed the CRM automation pipeline entirely
`src/app/api/crm/leads/public/route.ts` wrote to `LeadForm`+`MarketingLead` only — no scoring, no counselor assignment, no follow-up task — while the visually-similar `/api/leads` endpoint used by the homepage/contact forms has the full pipeline. Same underlying capability (`scoreLead`/`autoAssignCounselor`/`createFollowUpTask`), silently not applied depending on which page a lead came from.

### B.3 [FIXED — CRITICAL SEVERITY] `GET /api/students` had no authentication and leaked the entire student database
`src/app/api/students/route.ts` — calling it with no query parameters returned **every student record in the database**, including nested documents and payments, to any unauthenticated caller. Calling it with `?id=<any id>` returned that one student's full record (including documents/payments) to anyone who supplied/guessed the id. The frontend's own `useStudentId()` hook (`src/hooks/use-student-id.ts`) calls this exact endpoint with `?userId=...`, a parameter the route never implemented — the lookup silently failed by field-name mismatch, which is the only reason this wasn't already actively exploited by normal app usage; it was fully exploitable by direct request.

### B.4 [FIXED] `GET /api/counselor/students` had no authentication and trusted a client-supplied `counselorId`
`src/app/api/counselor/students/route.ts` — any unauthenticated caller could list all students; any authenticated counselor could view another counselor's caseload by changing a query string. **Confirmed this was not just theoretical**: both real UI callers (`counselor-student-360.tsx`, `sop-studio.tsx`) call this endpoint with **no `counselorId` at all**, meaning in production every counselor using these two screens was already seeing every student in the system regardless of assignment.

### B.5 [FIXED] `GET /api/counselor/hr-self` had no authentication and accepted an arbitrary `userId`
Despite the name "hr-self" (self-service), it took `userId` from the query string with no session check, exposing any employee's HR record, attendance, commission, bonus, increment, and performance history to anyone who supplied their id (or the first counselor in the DB, if omitted).

### B.6 [FIXED] `GET/POST/PATCH /api/counselor/tasks` had no authentication
Any caller could view any counselor's task queue via an arbitrary `assigneeId`, create a task "assigned" to any user, or mark any task belonging to anyone as completed.

### B.7 [FIXED] Seven `/api/student/*` resource routes had the exact same IDOR pattern already fixed once elsewhere in the codebase, but not here
`appointments`, `sop`, `notifications` (including a write-side IDOR letting anyone mark any student's notification read), `referrals`, `cv`, `visa-readiness`, `next-action` all took `studentId` from the query string/body with zero authentication — the identical bug class that a prior engineering pass had already found and fixed on `/api/student/profile` (see the `SEC-G fix (2026-09-18)` comment left in that file) but never propagated to its siblings.

### B.8 [NOT FIXED — documented, scoped as follow-up] Broad authentication coverage gap across the wider API surface
A repo-wide scan (methodology: flag any `route.ts` that does not import one of the known auth helpers — `@/lib/auth`, `@/lib/auth-middleware`, `@/lib/cron-auth`, `@/lib/unified-auth`, `@/lib/student-auth` — and does not reference `getServerSession`/`CRON_SECRET`/webhook-signature verification) flags **219 of 819** route files. This is a **method with false positives** (many are legitimately public — course/university/country listing pages, webhook receivers verified differently, cron jobs, public lead-capture forms) and the 8 concrete, confirmed, exploitable examples above (B.3–B.7) were pulled from this list and hand-verified before fixing. The remaining ~211 have **not** been individually hand-verified this session and must not be assumed either safe or vulnerable — see Section F for the recommended dedicated follow-up.

### B.9 [Documented, not changed] Three overlapping CRM lead tables (`LeadForm`, `MarketingLead`, `Lead`) remain in place
Per the "do not delete tables without explicit authorization" constraint, none were removed or merged. `Lead` was reinforced as the canonical automation-pipeline table (Section C); `LeadForm`/`MarketingLead` writes were preserved unchanged for backward compatibility with anything else reading them.

### B.10 [Documented, not changed] The Stack A / Stack B student duplication (Section A.3) was not merged
This is architecture-level surgery (which identity system is canonical, how to migrate existing rows, how to keep both login flows working during transition) that the task's own constraints require to be backed by "documented justification + backup + verified pre/post data integrity" — none of which can be responsibly done without a live database to test against (see Section D). It is reported here in full, with a concrete recommendation in Section F, rather than attempted blind.

All changes are additive/repair-in-place — no existing table was dropped, no existing feature was replaced, no new framework/DB/auth system was introduced. Every change reuses existing functions (`scoreLead`, `autoAssignCounselor`, `createFollowUpTask`, `findDuplicateLead`, `withAuth`, `authenticateUnified`, `authenticateStudentRequest`) already present in the codebase.

| File | Change |
|---|---|

## D. End-to-End Test Results (same student across all modules)

**Result: NOT VERIFIED — blocked at the infrastructure level, not attempted-and-failed, not skipped by choice.**

The task mandates registering one synthetic student via the real public registration form and tracing that exact student ID through DB persistence, CRM lead creation, counselor auto-assignment, student/counselor/admin portal visibility, application creation, and notifications/audit logs, verified via real DB queries/API responses.

This requires a running MySQL/MariaDB server. **None could be obtained in this sandbox**, despite an exhaustive search across every available channel:

| Channel tried | Result |
|---|---|
| `apt-get install mysql-server` / `mariadb-server` | **Blocked** — `apt-get update` fails against all three `deb.debian.org` mirror endpoints; sandbox egress is host-allowlisted and Debian's mirrors are not on the allowlist. |
| Filesystem search for a pre-installed binary | None found (`find / -iname "mysqld*"`, `dpkg -l | grep mysql/maria` — both empty). |
| Docker | Not present in the sandbox at all. |
| npm registry | No package provides a real, embeddable MySQL server binary (only client libraries: `mysql2`, `mysql`, `@types/mysql`, ORMs). |
| PyPI | No real MySQL server package exists (`mariadb-server`, `mysqlserver`, `static-mariadb`, etc. all 404). The `mariadb` PyPI package is a client binding only. |
| `mysql-mimic` (PyPI) | The only near-candidate — a **pure-Python MySQL wire-protocol shim**, not a database engine. Installed successfully (`pip install --break-system-packages` inside a venv) and inspected: it has no built-in storage/DDL engine at all — a user must hand-implement query execution in Python (it's designed for exposing a custom data source as MySQL-speaking, e.g. for BI-tool compatibility). It cannot run this repo's real Prisma migrations (`ENGINE=InnoDB`, foreign keys, JSON columns, MySQL-specific types). Using it would mean *fabricating* a database engine myself and calling the result "MySQL-verified," which would not be honest — so this path was **deliberately not pursued further**. |
| conda/anaconda, mysql.com, mariadb.org, GitHub release binary assets (`objects.githubusercontent.com`) | All host-unreachable from this sandbox (confirmed via direct `curl` probes; DNS resolves but connections fail — consistent with an egress allowlist that only permits `registry.npmjs.org`, `pypi.org`, `github.com`, `api.github.com`, `codeload.github.com`). |
| SQLite substitution (swap Prisma provider locally, never committed) | **Considered and rejected.** The schema and application code contain MySQL-specific types/attributes and likely raw SQL (`$queryRaw`) tuned for MySQL syntax. A pass/fail result against SQLite could not be trusted to mean anything about the real MySQL-backed production behavior — running it and reporting the outcome as "end-to-end verified" would risk being actively misleading, which the task explicitly forbids ("do not report completion without actual verification"). |

**What this means concretely:** every finding in Sections A–C above is either (1) a real execution result (`tsc`/`eslint`/`vitest`, which do not need a live DB) or (2) a static code-reading conclusion, clearly labeled as such. No claim in this report describes a live database write, read, or query result, because none could be produced.

**Exact access that would unblock Phase 5** (any one of these is sufficient):
1. SSH/credentials to a disposable staging MySQL/MariaDB instance (VPS or managed DB) with a `DATABASE_URL` this sandbox can reach, **or**
2. Expanding this sandbox's egress allowlist to include a Debian/MySQL package mirror or a Docker registry, **or**
3. A direct staging-environment URL + test credentials for an already-running instance of this application connected to a non-production database.

Given any of the above, the exact test that should be run next: `npm run db:push`/`migrate deploy` against the test DB → `POST /api/portal-auth/register` with a synthetic student → follow the repaired pipeline from Section C (Lead creation → `autoAssignCounselor` → `PortalStudentProfile.counselorId` populated) → `GET /api/portal-auth/session` (student) → `GET /api/counselor/students` / `/api/employee/students` (assigned counselor) → `GET /api/students?id=...` (admin) → confirm the same `studentId`/`Lead.id` appears consistently everywhere, and confirm `CrmAuditLog`/`AuditLog` entries were written.
