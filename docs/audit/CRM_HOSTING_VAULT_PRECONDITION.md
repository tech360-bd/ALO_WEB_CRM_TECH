# Hosting-Portal vault adapter: malware-scan precondition

**Decision:** Choose option (a) from issue #44: any future vault forward must require `scanForMalware()` to return `verdict: 'clean'`; an `unavailable` verdict is never eligible for external forwarding. Infected payloads are rejected before private storage. Scanner unavailability is rejected in production (the existing scanner's fail-closed behavior). In non-production, the existing local-ingestion fail-open behavior remains unchanged, but must not be reused as permission to forward externally.

**Implemented on this branch:** Both WhatsApp byte-write paths now scan downloaded bytes before `storePrivateFile()`: `ingestWhatsAppMedia()` and the separate direct path in `src/app/api/whatsapp/webhook/route.ts`. Both use the same fail-closed result validator. The external-forward authorization helper accepts only the exact frozen result object returned by the scanner wrapper, and only when its validated verdict is `clean`; an unavailable verdict is never accepted. Tests cover malware, production scanner unavailability, thrown scanner errors/timeouts, malformed scan results, clean-only authorization, and scan-before-store ordering in the direct webhook path. This closes the WhatsApp-path prerequisite; it does not claim that the vault adapter or any provider integration exists.

**Vault state:** No adapter is wired and the vault must remain disabled. No production configuration, credentials, provider migration, deployment, or external-storage processing destination is authorized by this decision. Do not enable vault forwarding until consent eligibility, the CRM-side adapter, its audit/idempotency behavior, and provider prerequisites have been independently reviewed and passed.
