## 2. The SQLite / MySQL question — answered

The brief asked which database each environment uses and which client the production image generates. Findings:

### 2.1 Production uses MySQL, and only MySQL

* `npm run build` = `prisma generate` (against `prisma/schema.prisma` → mysql) → `next build` → `prepare-standalone.mjs`. There is no second generate step and no `--schema` override.
* `src/lib/db.ts` constructs `new PrismaClient({ log })` from the generated mysql client; the libSQL branch is only reachable when `ALO_DB_DRIVER === 'sqlite'`.
* `ALO_DB_DRIVER` appears in **no** template: absent from `.env.example` and `.env.production.example` (verified with `grep`).
* The production container path is disabled: `Dockerfile` `CMD` prints `DISABLED` and `exit 1`; `docker-compose.yml` is marked `LEGACY / NOT USED FOR CURRENT PRODUCTION`; `ecosystem.config.cjs` throws on load.

### 2.2 SQLite exists only as an offline verification mirror

| Piece | File | Purpose |
| --- | --- | --- |
| Mirror schema | `prisma/verification-mirror/schema.sqlite.prisma` (499 KB) | SQLite dialect of the same 610 models, generated by `scripts/ai-workforce/mirror-schema.mjs` |
| Mirror client | output `node_modules/.prisma-sqlite/client`, `engineType = "client"` + `queryCompiler`/`driverAdapters` | Works with npm-registry-only networks (no engine binaries) |
| Runtime switch | `src/lib/db.ts:22-61` | Requires `ALO_DB_DRIVER=sqlite`, requires a `file:` `DATABASE_URL`, lazily requires the adapter, refuses if `process.getBuiltinModule` is missing |
| Dev config | `prisma/dev-sqlite.config.ts` | Explicit `--config`, uses the JS/WASM schema engine |

**Verification performed:** I re-ran `mirrorSchema(schema.prisma)` in memory and compared to the committed mirror → **identical** (`mirror in sync: true`). The mirror generator's documented transformations are provider swap, dropping MySQL native string types, `dbgenerated(_utf8mb4…)` → literal defaults, and `Json` → `String`. No model/field/index is added or removed.

**Conclusion:** the "mismatch" is a documented, bounded verification path — not a production misconfiguration. Residual risks:

| Risk | Severity | Correction |
| --- | --- | --- |
| Mirror can drift from `schema.prisma` silently (no CI gate runs `awf:mirror`/`awf:verify`) | Medium | Add CI job: regenerate mirror, `git diff --exit-code`, then run `awf:verify` against a throwaway SQLite file |
| `ALO_DB_DRIVER=sqlite` in a production `.env` would make the app refuse to boot (throws on non-`file:` URL) | Low (fail-closed, correct) | Add startup log line naming the active driver; add a config test asserting the variable is absent from production templates |
| SQLite mirror cannot validate MySQL-specific behaviour (collation, `TEXT` defaults, `VARCHAR(191)` limits) | Medium | Keep the MySQL 8.4 CI job as the authority; never accept SQLite as proof of MySQL compatibility |

## 3. Migration-chain vs schema drift

### 3.1 Independent static analysis (all 610 models)

Method: parse models with `@@map`/`@map`/`@ignore`; parse every migration statement (multi-column `ALTER TABLE` handled); compare columns per table.

| Check | Result |
| --- | --- |
| Models without `CREATE TABLE` anywhere in the chain | **0** |
| Schema columns with no corresponding `CREATE`/`ADD`/`MODIFY` | **0** |
| Tables created that no model maps | **1** — `_EmployeeToOffice` (Prisma implicit M2M; expected) |

### 3.2 The CI drift gate failure

`prisma migrate diff --from-migrations … --to-schema-datamodel …` replayed the chain into a shadow DB and produced **108 statements, 6 classified as real** by `scripts/ci/filter-lob-default-drift.mjs`. The six all concern TEXT/LONGTEXT columns in three migrations dated 2026-10-27 whose schema side uses plain `@default("…") @db.Text`, while the normaliser only recognises `@default(dbgenerated("(_utf8mb4'…')"))`.

| Aspect | Detail |
| --- | --- |
| Root cause | Guard limitation: MySQL renders `@default("") @db.Text` as an expression default; the diff round-trips a different textual form; the filter's matcher rejects it |
| Data impact | None observed or implied — the column default exists in both representations; no row is rewritten |
| Blast radius | 6 tables created by 3 unmerged-since-yesterday migrations: `permission_groups`, `permission_group_grants`, `system_settings`, `reports`, `module_build_requests`, `user_permission_overrides` |
| Recommended fix | Extend the normaliser to accept a plain literal default exactly matching the schema's `@default("X")` on a LOB-typed field; keep nullability/type/payload equality fatal; add 3 unit fixtures |
| Alternative (rejected) | `@default(dbgenerated(...))` on those fields — makes the fields required in `PrismaClient` create inputs, breaking 6 models' API |
| Alternative (rejected) | A new migration to MODIFY the columns — real DDL on live tables to satisfy a CI text match |
| Verification | Drift step passes with `0 real drift`; new fixtures prove a genuine mismatch still fails |
| Rollback | Revert one file (`filter-lob-default-drift.mjs`) + its test |

### 3.3 Constraints and indexes (spot audit of the newest tables)

Reviewed `permission_groups`, `permission_group_grants`, `system_settings`, `reports`, `module_build_requests`, `user_permission_overrides` in both schema and DDL: unique keys and secondary indexes match; the only FK (`permission_group_grants.groupId → permission_groups.id`, `ON DELETE CASCADE`) is present in the migration. `UserPermissionOverride.userId` intentionally has **no FK** to `User` — consistent with the rest of the schema, which uses string ids without relations in several places.

## 5. Tenant isolation

There is **no `tenantId` column** and no row-level security. Isolation is achieved by:

* string-owner columns (`partnerId`, `officeId`, `branchId`, `counselorId`, `createdBy`),
* `src/lib/access-control/object-scope.ts` and the central security engine,
* per-route filters.

This is functional today but has no database-level backstop. For memory and knowledge (the Phase 5 surface) the risk is higher because retrieval is semantic: a missing filter leaks another customer's facts. **Requirement for Phase 5:** every memory/knowledge read must take an explicit scope object (`tenantId`/`partnerId`/`subjectId`/`actorRole`) and the query builder must refuse to run without it; add a negative test per scope. Do not rely on call-site discipline.

## 7. Migration-safety rules adopted for this programme

1. **No `prisma db push`**, no `migrate reset`, no destructive SQL, ever, outside a disposable database.
2. New tables are additive and `IF NOT EXISTS` where the project already does so; **no** column drops or renames.
3. One migration per reviewable change, with an explicit rollback block in the file (existing convention — see `20261019100000_lead_acquisition_attribution/migration.sql`).
4. Every migration is first applied to a **disposable MySQL 8.4** instance seeded from a restored anonymised dump; the drift check and the 8 DB-backed suites must pass there.
5. Backfills are separate migrations with a bounded batch size and are never bundled with DDL.
6. Text/BLOB defaults must use one representation per table and be covered by the drift normaliser.
