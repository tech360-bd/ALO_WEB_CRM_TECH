# 06 — Search Console implementation

**Cost:** FREE, no billing account. **Property:** Domain property for `aloeducation.com`.
**Code of record:** `src/lib/seo/search-console-client.ts`,
`src/app/api/seo/search-console/*`, `src/app/api/google/analytics/report` (GA4 side),
`src/app/robots.ts`, `src/app/sitemap.ts`, `src/lib/seo/schema-helpers.ts`.

---

## 1. What is implemented in code

| Surface | Endpoint / file | Purpose |
|---|---|---|
| Connection check | `GET /api/seo/search-console/status` | Credential mode, property, whether Google answers |
| Search performance | `GET /api/seo/search-console/performance` | Clicks, impressions, CTR, average position by `query` / `page` / `country` / `device` / `date` |
| Sitemaps | `GET /api/seo/search-console/sitemaps` | Submitted/indexed counts, warnings, errors, whether ALO's sitemap was submitted at all |
| Opportunity ingest | `POST /api/seo/search-console/ingest` | Feeds live Search Analytics rows into the **existing** `src/lib/seo-engine.ts` opportunity engine |
| Aggregate Google status | `GET /api/google/status` | Search Console row with `liveVerified` and cost tier |
| robots.txt | `src/app/robots.ts` | See §3 |
| sitemap.xml | `src/app/sitemap.ts` | See §3 |
| Structured data | `src/lib/seo/schema-helpers.ts`, rendered site-wide in `layout.tsx` | Organization / EducationalOrganization JSON-LD |

Design rules carried by the client (`src/lib/seo/search-console-client.ts`):

- **No credential → `NOT_CONFIGURED`**, never an empty result set that reads as "no traffic".
- A genuinely empty window is `READY` with zero rows — distinguishable from the above.
- CTR and average position in `totals` are **impression-weighted**, not plain means, so one
  low-impression query cannot dominate the summary.
- `dataState: 'final'` is requested so partially-processed days are not counted as real.
- Timeouts (15s), one 401 retry, no retry loop.
- Google's own error `reason` is surfaced — that string is what tells an operator the
  difference between "API not enabled" and "service account not added to the property".

## 2. What remains BLOCKED

| Specification requirement | Status | Why |
|---|---|---|
| Domain property verified | **BLOCKED** | DNS TXT action at the DNS provider |
| Search Console API authentication | **BLOCKED** | Needs the service account created, added to the property, `webmasters.readonly` |
| Live performance query | **BLOCKED** | Same |
| Indexing inspection | **BLOCKED** | Needs the credential; the URL-Inspection API is not implemented (see §5) |
| Core Web Vitals (field data) | **BLOCKED** | CrUX data is served through the Search Console API — same credential |
| Sitemap submitted/indexed counts | **BLOCKED** | Same credential |
| Canonical-tag audit across all pages | **PARTIAL** | Metadata-driven per route; no exhaustive crawl audit was performed |
| Mobile usability / international targeting | **PARTIAL** | Not verifiable without Search Console access |
| Structured data validity | **PARTIAL** | Organization JSON-LD is rendered site-wide and unit-tested for serialisation safety; per-page-type schema is present for courses/universities; Google's Rich Results validator has not been run against production |
| Google site-verification meta tag | **PARTIAL** | Supported via `GOOGLE_SITE_VERIFICATION_TOKEN` in the layout; needs a real token. DNS verification is preferred anyway |

## 3. robots.txt and sitemap.xml (implemented, audited)

### robots.txt — `src/app/robots.ts`

Explicit lists rather than wildcards, for two opposite jobs:

- **Allowed:** every public marketing page — country, course, university, scholarship, visa,
  IELTS, blog, guide.
- **Disallowed:** `/api/`, `/admin/`, `/crm/`, `/super-admin/`, `/counselor/`, `/employee/`,
  `/application-manager/`, `/dashboard/`, `/hr/`, `/hrm/`, `/user-guide/`, `/partner/`,
  `/partner-admin/`, `/student/`, `/parent-portal/`, `/university-portal/`, `/portal/`,
  `/review/`.
- **Utility (disallowed):** `/offline`, `/forgot-password`, `/reset-password`, `/verify-email`.
- `/login` and `/register` are deliberately **not** disallowed: they are legitimate entry pages
  users search for, and blocking them produces "indexed though blocked" noise.

`/review/[token]` is disallowed specifically because the token **is** the authorisation —
letting Googlebot fetch it puts a live capability token in a crawl log.

The file states, correctly, that robots.txt is a crawl directive and **not** access control;
every listed route is separately authenticated in code.

### sitemap.xml — `src/app/sitemap.ts`

`force-dynamic`, composed from nine sources, each gated by the public-content policy so that an
unpublished or internal record cannot leak into the index. It is regenerated by the existing
`/api/cron/sitemap-regeneration` job.

**Never indexed:** private student dashboards, CRM administration, authentication pages, private
application records, internal APIs, duplicate filtered URLs, sensitive student documents. The
robots file above is the enforcement for the crawl side.

## 4. Reporting that now spans both APIs

The admin SEO view uses Search Console for **search** performance and the GA4 Analytics Data
API (added in this pass) for **acquisition and on-site** behaviour. They answer different
questions and are deliberately not merged or averaged:

| Question | Source |
|---|---|
| Which queries brought impressions? | Search Console |
| Which landing pages started sessions? | GA4 Analytics Data API (`preset=landingPages`) |
| Organic vs referral vs direct split | GA4 `preset=channels` (`sessionDefaultChannelGroup`) |
| Which pages does Google refuse to index? | Search Console URL inspection — **BLOCKED** |

## 5. Deliberately not implemented

| Item | Reason |
|---|---|
| **Indexing API** (on-demand URL submission) | Google restricts it to `JobPosting` and `BroadcastEvent` structured data. Using it for course or destination pages violates the terms and risks the property |
| **URL Inspection API automation** | Its quota (2,000/day per property) is ample, but a nightly crawl-inspection loop would be a Google dependency in a cron job for a benefit the Search Console UI already gives weekly. A manual/operator-triggered call is the right shape and is not built |
| **`web-vitals` client beacon** | Field data belongs in CrUX via Search Console. A second client-side reporting path would compete with the GA4 event stream the specification requires to be single |
| A second sitemap generator | `src/app/sitemap.ts` already exists and is cron-regenerated |

## 6. Operator checklist

1. Verify the **Domain** property by DNS TXT (`02-google-account-setup.md` §3d).
2. Submit `https://aloeducation.com/sitemap.xml`.
3. Create the service account and add it to the property as **Restricted** (read) — domain
   verification is *not* inherited.
4. Set `GOOGLE_SEARCH_CONSOLE_CREDENTIALS_JSON` and `GOOGLE_SEARCH_CONSOLE_SITE_URL`.
5. `GET /api/google/status?live=true` → the `SEARCH_CONSOLE` row must show `PASS`. If it shows
   `BLOCKED`, read `reason`: it will name the exact missing grant.
6. `GET /api/seo/search-console/performance?days=28&dimensions=query` → `status: READY`.
7. `GET /api/seo/search-console/sitemaps` → `expectedSitemapSubmitted: true`.
8. Review **Pages → Indexing** in the Search Console UI weekly; fix what Google lists.
9. After two weeks of data, `POST /api/seo/search-console/ingest` to feed the existing
   opportunity engine.
